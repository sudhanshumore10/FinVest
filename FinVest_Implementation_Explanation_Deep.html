1. System Architecture Overview

FinVest is a server-rendered Flask application. The project follows a layered pattern rather than placing all logic in one file. The major layers are configuration/bootstrap, models, routes, services, utilities, and presentation templates. The goal of this separation is to keep request handling, business logic, persistence, and UI concerns independently manageable.

The bootstrap sequence begins from backend/main.py and backend/app/__init__.py. The app factory initializes Flask, loads configuration, initializes SQLAlchemy, initializes MongoDB, registers the blueprints, and then attaches cross-cutting hooks like schema checks, automation execution, response-time capture, and shared template context injection.

The practical effect is that almost every page render in the application is not a simple HTML response. Before the response is produced, the app can ensure database shape, refresh session activity, run due recurring financial jobs, and populate template-wide metadata such as unread notification count and current display currency.

1.1 Application Startup Flow

  1. backend/main.py imports create_app() and creates the Flask application object.
  2. backend/config.py provides MySQL and MongoDB settings.
  3. extensions/db.py initializes SQLAlchemy as the main ORM and transaction manager.
  4. extensions/mongo.py initializes the MongoDB client for log and snapshot storage.
  5. The app registers blueprints for auth, dashboard, budgets, goals, categories, notifications, reports, and transactions.
  6. Before each request, the app runs schema checks, touches the active session, and runs due automation jobs such as salary posting and recurring transactions.
  7. After each request, response time is measured and stored in app config for admin performance visualization.
  8. A context processor injects notification count, display currency, display symbol, exchange rates, selected language, and available languages into every rendered template.
  9. A Jinja filter named money converts amounts into display-format currency strings.

1.2 Why This Architecture Matters

If the evaluator asks why everything was not placed inside route files, the correct explanation is that route files should stay focused on HTTP input/output and authorization, while service files hold reusable business logic. This project follows that pattern especially for automation, reports, notifications, currency handling, schema upgrades, and session tracking. It makes the code easier to maintain and easier to explain by feature.

2. Data Architecture and Persistence Model

The project uses two persistence stores. MySQL is the primary relational store for finance domain objects and application state. MongoDB is the secondary document store for flexible event-style data such as activity logs and report snapshots.

2.3 Schema Evolution Strategy

The newer synced code introduced schema_service.py. This exists because the project evolved after the first database version. Instead of assuming the local database already has every new column, the app checks the current schema at runtime.

  • If users.security_answers is missing, it is added.
  • If user_settings.language is missing, it is added.
  • If user_settings.monthly_salary_last_added is missing, it is added.
  • If new tables such as active_sessions or recurring_transactions do not exist, db.create_all() is used to create them.

This is a lightweight runtime migration strategy. It is not as formal as Alembic, but it works well for a classroom project where the schema changes rapidly and teammates may run the app against older local databases.

3. Part A: User Story Wise Deep Explanation

US-1: Register and log in so the user can access the finance dashboard

Main implementation files: auth_routes.py, auth.html, auth.css, user_model.py, active_session_service.py, admin_service.py.

Detailed behavior

  1. The user opens /auth. The auth template renders login and signup in a switchable panel interface.
  2. During signup, the backend reads username, email, password, confirm password, and five recovery answers.
  3. The backend validates:
    • username format using regex
    • email uniqueness
    • reserved admin email usage
    • password complexity
    • password confirmation match
    • presence of all recovery answers
  4. Recovery answers are normalized and then individually hashed before being bundled into a JSON string stored in users.security_answers.
  5. Password is hashed using Werkzeug, not stored in plain text.
  6. After insertion, the code automatically creates the user’s settings row, default categories, and default account. This gives the new user a usable environment immediately after registration.
  7. During login, the backend tracks login attempts using Flask session keys. If too many failures happen in the cooldown window, the user is temporarily blocked from retrying.
  8. On successful login, session keys are set and a random session token is generated. That token is stored both in Flask session and the active_sessions table through start_active_session().
  9. The login action is recorded via log_activity().
  10. If role is admin, the route redirects to admin dashboard. Otherwise it redirects to user dashboard home.

Technical strengths

  • Registration immediately seeds usable finance objects.
  • Auth state is tied to auditable active-session rows.
  • Password reset does not require mail infrastructure.

Honest difference from original story

The original story mentioned password reset through email token. The current code uses security-question based reset instead. Teammates should say this clearly if asked.

US-2: Set currency, locale, month start, and user preferences

Main implementation files: dashboard_routes.py, user_settings_model.py, account.html, currency_service.py, i18n_service.py.

The /account page lets users update display and planning preferences. Currency affects how amounts are shown through the context processor and template filter. Language and locale affect display normalization. Month-start day is constrained to 1–28 to avoid invalid calendar edges. Monthly salary is stored here and later consumed by the automation service, so this settings module is not just cosmetic.

US-3: Add income entries so inflows are tracked

Main implementation files: transaction_routes.py, transaction_service.py, transaction_model.py, transactions.html.

The user adds a transaction with type income. The route validates account/category ownership, parses amount/date, stores the row, and then calls the transaction service to add the amount to the account balance. This means the balance screen is not recomputed lazily later; it is updated as part of the write path.

US-4: Add expense entries and categorize them

Expense flow is identical structurally to income flow, but the transaction effect is negative. The expense must be mapped to a valid user-owned category. Category totals later drive reports, dashboard pie chart segments, budget comparisons, and top-spending-category calculation.

US-5: Set category budgets and get threshold alerts

Main implementation files: budget_routes.py, budget_model.py, notification_service.py, budgets.html, home.html.

Each budget is scoped to user, category, month, and year. Current-month expense transactions are aggregated by category. The app computes spending percentage against the limit and uses this for both UI status and notification generation. At 80%, a warning notification is created. At 100% or more, a budget exceeded notification is created.

US-6: Create savings goals and track progress

Main implementation files: goal_routes.py, goal_model.py, goals.html, dashboard home.

Goals are stored independently from transactions because the user may want to track savings progress manually rather than deriving it from a single transaction category. Each goal has target, current amount, deadline, and status. The app supports full update plus a dedicated add-amount action for incremental progress.

US-7: View charts and KPIs to understand finances quickly

Main implementation files: dashboard_routes.py, home.html, dashboard.css.

The server builds the dashboard state in _build_dashboard_data(). This includes total balance, monthly income, monthly expense, average monthly spending, recent transactions, budget summaries, top goal, top spending category, and chart-ready data. The home page uses server-provided chart widths and conic-gradient styles rather than a heavy JS chart dependency.

US-8: Search and filter transaction history effectively

The transaction list supports server-side filters for type, category, date range, and amount range. This means the SQL query is narrowed before rendering. The result is cleaner than loading all transactions and filtering in the browser. Export is handled from the reports module, where transaction data can be downloaded after summary generation.

US-9: Import transactions from CSV

Main implementation files: transaction_routes.py, dummy_transactions.csv sample file.

The import route validates headers, normalizes rows, parses amount/date, creates missing categories if needed, resolves an account, checks duplicates through a composite identity rule, and then inserts only non-duplicate transactions. Imported rows still pass through the financial side effect path, so balances remain correct.

US-10: Secure access and auditable changes

Authorization is handled through decorators and role checks, especially for admin routes. Auditability comes from activity logging and active-session tracking. Together, they let the app answer both “who performed this action?” and “who is active right now?”

US-11: Welcome / onboarding guide

The project implements onboarding in two stages. First, there is a public onboarding/landing page at /. Second, there is a dismissible quick guide inside the authenticated dashboard. This is useful in evaluation because the team can explain onboarding as a staged UX rather than a single page.

US-12: View monthly income vs expense comparison

The dashboard groups transaction totals over the last four months, computes the largest month value, and converts each month’s income and expense values into percentage widths. The template then renders the bars using those widths. This means the visual chart is directly derived from server-side finance aggregation.

US-13: View category-wise spending analysis

Current-month expense transactions are grouped by category and sorted descending. The route builds a conic-gradient pie chart style string and a separate legend list with category name, amount, percentage, and color. This gives both a visual representation and a textual representation for the same data.

US-14: View average monthly spending

The route computes monthly expense totals across the tracked months and averages only the months where expense is non-zero. That prevents zero-activity months from artificially lowering the average.

US-15: Admin views account activity history

The admin dashboard reads activity logs from MongoDB first, then falls back to SQL if Mongo is unavailable or empty. It transforms them into a unified row structure with user name, action, details, timestamp label, and normalized day key for daily charting. This allows both history viewing and “today’s activity” metrics.

US-16: View budget vs actual spending

This is implemented both on the budgets page and on the home dashboard. The route computes actual spend per budget category using current-month expense transactions and then attaches percentage values for visual warning states.

US-17: Edit or delete transactions

Editing a transaction is not a simple overwrite. The code must reverse the previous account effect, replace the transaction attributes, and then apply the new effect. Deleting must also reverse the financial impact before removing the row. This is an important detail to explain if someone asks how consistency is preserved.

US-18: Add notes or descriptions to transactions

Descriptions are stored in the transaction row and reused everywhere: transaction history, dashboard recent transactions, CSV export, JSON backup, and report analytics payloads.

US-19: Mark notifications as read

Notifications include an is_read flag. The notification routes support marking a single notification read or marking all unread notifications read. The header bell shows unread count using a shared context processor.

US-20: View transaction history for a selected date range

Date range filtering is implemented directly in the transaction query through start-date and end-date comparisons. This supports historical review, filtered export, and budget/report investigation.

4. Part B: Module Wise Deep Explanation

Module 1: Authentication and Authorization

This module combines registration, login, logout, security-question based reset, login throttling, admin seeding, and active-session tracking. It uses Flask session for short-lived request-state identity and MySQL for persistent user identity. Admin recognition depends on role and reserved admin email policy. The module also acts as the initial data seeding point for new users by creating default settings, categories, and account immediately after registration.

Module 2: Transaction Management

This module is the financial event layer. Every transaction links user, account, and category. The route layer validates ownership, while the service layer applies monetary effects to the linked account. CSV import belongs conceptually here because it ultimately creates the same transaction records and must preserve the same balance rules.

The critical design principle is: transactions are stored as history, account balances are stored as fast summaries, and the application keeps them synchronized in the write path.

Module 3: Category Management

Categories are user-specific and seeded with sensible defaults. This lets every user have a clean initial set without depending on a global static master list. The module becomes essential because transactions, budgets, and reports all depend on category identity.

Module 4: Dashboard Module

The dashboard is the synthesis layer of the application. It does not merely fetch rows; it builds business-facing summaries. Total balance comes from accounts, monthly KPIs come from current-month transactions, chart series come from grouped transaction history, and budget/goal cards come from planning modules. The dashboard also includes the quick-guide behavior and the profile-menu based navigation pattern defined in the layout template.

Module 5: Budget Planning

This module handles two related things: monthly planning budgets and recurring expenses. Planning budgets compare expected vs actual monthly category spend. Recurring expenses feed the automation engine, which creates actual transaction rows later. This makes the module more powerful than a static budget sheet: it becomes a spending-control plus automation-definition module.

Module 6: Reports and Analytics

This module turns transaction history into summarized decision-support data. The report service computes: total income, total expense, net, average monthly spending, savings rate, top expense category, income-source contribution, month-wise net chart, trend rows, and full transaction export sets. Snapshot saving to Mongo makes the reporting layer persistent beyond immediate page rendering.

Module 7: Reminder and Notifications

This module works by synchronizing logical reminders into stored notification rows. It is driven by business conditions, not manual entry. Examples include welcome notifications, budget threshold notifications, and goal deadline notifications. By using a reference key, the same logical event does not spam the user repeatedly.

Module 8: Data Export and Backup

CSV export provides a spreadsheet-friendly version of transactions plus analytics summary. JSON backup provides a more system-friendly snapshot including user profile, settings, accounts, categories, recurring transactions, goals, raw transactions, and analytics. This module supports portability and review use cases.

Module 9: Saving and Goals

This module stores savings targets in a way that is independent from raw transaction classification. That is a useful design for personal finance because savings progress may not always map to a single “savings” transaction category. The dashboard highlights top goal progress, and notifications provide deadline awareness.

Module 10: Account Management

The account module controls both user profile and financial account containers. The same page lets the user update name, password, currency/locale/language settings, salary defaults, and the list of Cash/Bank/UPI accounts. This is why the top-right profile dropdown points into account settings instead of maintaining a separate disjoint page.

Module 11: Admin and System Module

This module is one of the most technically rich parts of the project. It merges user management, activity auditing, system-wide financial visibility, login trend visualization, performance monitoring, and active-session counting. The admin dashboard does not rely on a single data source; it pulls from MySQL, MongoDB, request timing state, and session-tracking tables.

5. Services Layer Deep Dive

automation_service.py

This service introduces automated financial behavior.

  • Monthly salary: If the user has configured a monthly salary and it has not yet been posted for the current month, the service inserts an income transaction into the default account and records the month in monthly_salary_last_added.
  • Recurring transactions: For each active recurring row, if the next run date is due, the service inserts real transactions and advances the recurrence schedule. It can catch up multiple missed runs because it uses a loop, not a single-if check.

This is a strong talking point because it shows the app goes beyond manual CRUD and includes lifecycle automation.

active_session_service.py

This service defines the active session window, starts sessions at login, touches sessions during authenticated requests, removes stale ones, and counts current active sessions. It is the backbone of “logged in now” monitoring shown to admin.

report_service.py

This service is effectively the analytics engine. It builds filtered transaction queries, computes totals, builds grouped chart rows, generates trend statements, computes savings rate, identifies top categories/income sources, and optionally stores deduplicated report snapshots in MongoDB using a SHA-256 fingerprint.

notification_service.py

This service centralizes all system-generated notifications. It creates a welcome notification, checks budgets against monthly expense totals, checks goal deadlines, and exposes unread count helpers. The use of reference_key is critical because it guarantees the same logical alert is not inserted repeatedly.

currency_service.py and i18n_service.py

These services separate presentation rules from route logic. Currency conversion works from INR into display currencies using predefined exchange rates, and language normalization collapses inputs into supported codes like English, Hindi, and Marathi.

schema_service.py

This service protects older local databases from crashing under the new code. It checks live schema and applies incremental corrections so the synced project can still run even if the earlier database lacked the newest columns.

7. Honest Differences Between Original Requirement Wording and Current Code

  • Password reset is security-question based, not email-token based.
  • Transaction filtering is implemented strongly, but pagination is not present in the current code.
  • The home dashboard uses server-generated widths and CSS-based pie chart styling, not a full external chart library on that page.
  • Language support is normalization and display-preference oriented, not a full translation framework.
  • Automation runs inside the request lifecycle instead of a separate dedicated worker process for all features.

8. High-Probability Evaluator Questions and Strong Answers

QuestionSuggested Answer
Why use both MySQL and MongoDB?MySQL stores structured finance entities and relational links. MongoDB stores flexible event and snapshot data like activity logs and report snapshots, which are document-shaped and append-heavy.
How do recurring transactions work if the user logs in after many days?The automation service loops while the recurring item’s next run date is less than or equal to today, so missed executions are caught up and the schedule is advanced correctly.
How do you avoid duplicate notifications?The notification service checks a logical reference_key before inserting. If that key already exists for the same user and alert type, it skips the duplicate.
How is total balance calculated?It is the sum of balances stored across the user’s accounts. Those balances are maintained incrementally whenever transactions are added, edited, deleted, or auto-generated.
How is average monthly spending computed?The dashboard groups expenses month-wise, keeps only months with positive expense totals, and computes the arithmetic mean of those months.
What if the database is from an old version and missing columns?The schema service checks the live MySQL schema on request startup and adds missing fields like security answers, language, and salary tracking fields if necessary.
How do you prevent duplicate CSV imports?Before insertion, the import flow checks whether a transaction with the same user, account, category, type, amount, date, and description already exists. Matching rows are skipped.
How does the admin know who is online now?Through the active-sessions table, where session tokens are touched during authenticated requests and stale sessions are cleaned by time window.
Why is salary configuration inside account settings?Because salary is user-specific financial configuration, not global system configuration. It also directly feeds the recurring automation logic.
How do you keep balances correct when editing a transaction?The code reverses the old financial effect from the old account before applying the new transaction values to the correct account.

9. Final Study Summary for Teammates

The best way to explain FinVest in tomorrow’s review is this:

  1. It is a Flask finance platform with MySQL as the primary transactional store and MongoDB as a secondary log/snapshot store.
  2. Users register, receive default settings/categories/account automatically, and then manage transactions, categories, budgets, goals, reports, and notifications from a server-rendered dashboard.
  3. Transactions are the event ledger. Account balances are maintained as fast summaries.
  4. Budgets, goals, notifications, reports, and admin views all derive insight from the transaction data.
  5. Automation adds real value through monthly salary posting and recurring transactions.
  6. Admin is not just a user list; it includes activity auditing, active-session counting, trend visibility, and performance insights.

If teammates explain the system in those terms, they will sound technically clear, honest, and confident.
